## Known GitHub evidence to verify locally

The GitHub backup currently appears to contain:

### Express proxy

`frontend/server/routes.ts` proxies:

`GET /api/watchlist/security-search`

to the FastAPI Watchlist search endpoint.

The proxy currently appears to:

* manually create an `AbortController`
* abort the upstream request after exactly 10,000 milliseconds
* call a backend whose FMP requests independently have a 10-second deadline
* return HTTP 502 on proxy timeout

That creates effectively zero timing margin between the backend deadline and proxy deadline.

### React page

`frontend/client/src/pages/watchlist.tsx` currently appears to:

* debounce the manual-add search by 300 milliseconds
* use query key:
  `['watchlist-security-search', debouncedSearch]`
* call the Express proxy with plain `fetch()`
* check only `response.ok`
* return the JSON body without checking for a payload-level `error`
* set `retry: false`
* not pass React Query’s supplied abort signal into `fetch()`

Verify all of this against the local code before editing.

## Required proxy correction

The proxy deadline must be longer than the backend’s bounded provider deadline plus reasonable processing/network margin.

Unless local evidence proves a different backend timeout, change the proxy security-search deadline from 10 seconds to 20 seconds.

Prefer the existing runtime’s native bounded timeout mechanism, such as:

`AbortSignal.timeout(20_000)`

instead of leaving an uncleared manual timer.

Preserve:

* the same proxy path
* the same backend target
* the same authentication/header helper
* the same query and limit forwarding
* the same canonical response payload

For upstream failures:

* preserve the upstream HTTP status where safe
* return a compact usable JSON error
* do not turn upstream 502/503/timeout into HTTP 200
* do not leak the upstream body when it could contain sensitive information
* distinguish proxy timeout from general proxy failure

Do not solve this by removing the timeout entirely.

## Required React Query correction

Update the existing security-search query only.

Use React Query’s query-function context:

* accept its `signal`
* pass that signal into browser `fetch`

This must cancel superseded searches when the debounced query key changes.

After receiving JSON:

* if the HTTP response is not successful, throw an appropriate search error
* if the JSON payload contains `error`, throw an appropriate search error even when HTTP status is 200
* only treat `results: []` without an error as a legitimate zero-result response
* validate that `results` is an array before rendering it

Do not silently normalize malformed or failed payloads to an empty result array.

Configure one bounded retry for transient search failures only.

Retryable examples:

* network failure
* proxy timeout
* HTTP 502
* HTTP 503
* backend `provider_error`

Do not retry:

* abort caused by a superseded query
* ordinary 4xx validation responses
* a legitimate zero-result search

Use a short bounded retry delay. Do not create a long retry loop.

Keep:

* the 300ms debounce
* one-character symbol support because valid US tickers can contain one character
* the existing query key
* the existing selected-security requirement
* the existing canonical ticker returned by the backend
