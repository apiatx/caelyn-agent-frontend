Frontend-only task: send screen_context with every /api/query chat request so the agent can see the current page contents.

Scope:
Frontend only.
Do not touch backend files.
Do not change page UI.
Do not change page layouts.
Do not change page data fetching.
Do not change filters, sorting, tables, widgets, or TradingView behavior.
Do not refactor unrelated components.
Do not create branches or PRs.
Only serialize the current page’s already-rendered / already-loaded data into `screen_context` when sending chat requests.

Goal:
When the user asks the chat questions like:
- “What looks good here?”
- “Which of these is strongest?”
- “What should I focus on from this page?”
- “What do you think of this chart?”
the backend agent receives enough context to understand the current route, page, tab, filters, visible rows, visible symbols, freshness, and TradingView widget state.

Backend is already ready:
- /api/query accepts `screen_context`
- backend preserves route/page/tab/selected_symbol/visible_symbols/visible_rows/filters/sort/rendered_sections/freshness/tradingview_context
- backend routes ambiguous “what looks good here?” queries based on screen_context.page
- no backend changes needed

Your job:
Attach `screen_context` to every /api/query request.

Required top-level payload field:
```ts
screen_context: {
  route?: string;
  page?: string;
  tab?: string;
  selected_symbol?: string;
  visible_symbols?: string[];
  visible_rows?: any[];
  filters?: Record<string, any>;
  sort?: Record<string, any>;
  rendered_sections?: Record<string, any>;
  freshness?: Record<string, any>;
  cache_metadata?: Record<string, any>;
  tradingview_context?: {
    symbols?: string[];
    raw_symbols?: string[];
    tradingview_symbol?: string;
    tradingview_symbols?: string[];
    timeframe?: string;
    interval?: string;
    active_widget?: string;
    active_widget_symbol?: string;
    layout?: string;
    source?: string;
    widgets?: Array<{
      raw_symbol?: string;
      symbol?: string;
      tradingview_symbol?: string;
      timeframe?: string;
      interval?: string;
      source?: string;
    }>;
  };
}

Important:
Use the exact field name screen_context.

Do not send unlimited full datasets. Send the current visible rows/top rows only.

Recommended frontend limits:

visible_rows: max 25 rows
visible_symbols: max 100 symbols
rendered_sections: concise summaries/section-level objects only
no huge raw blobs
no secrets/tokens
no hidden user credentials
no unnecessary full API payload dumps

Implementation approach:

Locate the central chat request builder / API call to /api/query.
Add a reusable helper such as buildScreenContext() or equivalent.
The helper should inspect the current route/page state and include the currently loaded/visible data that already exists in the frontend.
Pass the generated screen_context into every chat request.
Do not trigger new page data fetches solely to build screen_context.
Do not change what pages render.
Do not change existing page endpoint calls.
