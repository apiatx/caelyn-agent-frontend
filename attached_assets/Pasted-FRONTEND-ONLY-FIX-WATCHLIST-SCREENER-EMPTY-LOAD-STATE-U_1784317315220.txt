Correction:

The issue is NOT that the previous watchlist’s rows show for 10 seconds.

The issue is:

1. On startup, page return, tab return, or route return, the Watchlist screener section shows 0 tickers / blank data for too long.
2. This happens in the main Watchlist screener section itself.
3. The UI should not drop to empty rows while refetching if last-known watchlist data exists.
4. Upcoming Earnings is still incorrectly scoped:
   - Primary shows Strong Bases earnings.
   - Favorites shows no earnings.
   - Earnings must follow the currently viewed watchlist/tab.

Goal:

Fix two things:

A. Watchlist screener should use last-good cached rows / keep previous valid rows visible while refetching.
B. Upcoming Earnings should filter to the currently viewed watchlist symbols.

PART 2 — ADD LAST-GOOD ROW RETENTION FOR SCREENER
==================================================

The Watchlist screener should not blank out during normal refetches if it has valid previous data.

Implement a last-good row strategy.

Rules:

- Maintain lastGoodRowsByWatchlistId.
- Key it by active watchlist id.
- When a watchlist successfully loads non-empty rows, store them.
- During refetch/loading where current rows are temporarily undefined/empty, render lastGoodRows for that same watchlist id.
- Show a subtle “Refreshing…” indicator instead of a blank table.
- Do not show stale rows from a different watchlist id.
- Do not use Strong Bases rows for Primary.
- Do not use Primary rows for Strong Bases.
- Do not use normal watchlist rows for Favorites unless they are favorite rows.

Important:

This is not the same as showing previous tab data.
Only reuse last-good data for the SAME watchlist id/tab.

Example:

Primary has 302 rows.
User leaves page and comes back.
Query refetches.
Do not show 0 rows.
Show last good Primary rows with “Refreshing…” until new Primary rows arrive.

Strong Bases has 20 rows.
User switches to Strong Bases.
Only show last good Strong Bases rows if available.
Do not show Primary rows.

Favorites has 29 rows.
Use last good Favorites rows for Favorites.

PART 3 — FIX EMPTY STATE VS LOADING STATE
==================================================

Do not render “0 tickers” / blank table while data is loading/refetching and last-good rows exist.

Correct behavior:

If loading and no last-good rows:
- show skeleton/loading state

If refetching and last-good rows exist:
- show last-good rows
- show subtle “Refreshing…” badge

If loaded and true row count is 0:
- show real empty state:
  “No tickers in this watchlist.”

The empty state should only appear after the selected watchlist has finished loading and truly has zero tickers.

Create one reliable selected tab symbol source for earnings.

selectedTabKind:

selectedTabRows:

selectedTabSymbols:

  Array.from(favoritesSet).map(uppercase)

  selectedTabRows.map(row.ticker).map(uppercase)

Do not derive earnings from stale allTickerSymbols if that value can point to the wrong tab.

PART 5 — FIX UPCOMING EARNINGS FILTER
==================================================

Upcoming Earnings must use selectedTabSymbols.

Filter:

const selectedSet = new Set(selectedTabSymbols.map(s => s.toUpperCase()));

const filteredEarnings = allEarnings.filter(e =>
  selectedSet.has((e.ticker ?? e.symbol ?? "").toUpperCase())
);

Rules:

Primary selected:
- earnings tickers must be subset of Primary tickers only

Strong Bases selected:
- earnings tickers must be subset of Strong Bases tickers only

Favorites selected:
- earnings tickers must be subset of Favorites tickers only

If selectedSet is empty:
show:
“No upcoming earnings for this watchlist.”

If selectedSet has tickers but no matching events:
show:
“No upcoming earnings for this watchlist.”

Do not show unfiltered global earnings.
Do not show Strong Bases earnings when Primary is selected.
