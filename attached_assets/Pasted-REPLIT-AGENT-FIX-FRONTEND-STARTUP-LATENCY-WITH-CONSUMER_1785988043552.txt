# Proven audit findings

The prior read-only audit established:

## Primary cause

The complete Primary Watchlist detail response:

```text
/api/watchlist/{primaryId}
```

is approximately:

```text
6.3 MB
462 tickers
3.9–5.0 seconds
```

It is currently prefetched on every authenticated application startup, regardless of which route is open.

That includes Home and other pages that do not render the full Watchlist Screener payload.

## Secondary causes

1. `/api/watchlist/list` is requested twice during authenticated startup:

   * once through React Query prefetch
   * once through a separate raw `safeFetch()`

2. Approximately 22 requests can begin together when authentication becomes active.

3. Retry settings can expand the burst to approximately 66 attempts.

## Ruled out by the audit

* Workspace memory saturation
* Duplicate frontend dev servers
* Vite/HMR loops
* Frontend proxy overhead as the main cause
* Watchlist taxonomy calculations
* The proposed atomic Neon save, which does not exist yet

Use the existing audit report as evidence, but independently verify the live code before editing.

# Critical architectural principle

Backend freshness and browser fetching are different concerns.

The backend may already maintain current data through:

* scheduled jobs
* providers
* caches
* Neon persistence
* Watchlist refresh logic
* options collectors
* theme calculations
* macro collectors

The browser does not need to download every full page response at login merely because the backend already maintains that data.

Use this model:

```text
Backend/cache = complete warehouse

Home = compact live dashboards and summaries

Destination page = full detailed dataset
```

Removing an unnecessary frontend prefetch must not disable backend data collection.

# Contract 3 — remove duplicate `/api/watchlist/list`

The current global flow effectively performs both:

```ts
prefetchQuery(["/api/watchlist/list"])
```

and:

```ts
safeFetch("/api/watchlist/list")
```

The second raw fetch bypasses React Query deduplication.

Replace this with one React Query-owned read wherever the list is actually needed.

Preserve the exact query key:

```ts
["/api/watchlist/list"]
```

Preserve current authentication headers.

Preserve Primary identification precedence:

1. `is_primary`
2. `kind === "primary"`
3. `type === "primary"`
4. case-insensitive `name === "primary"`
5. case-insensitive `title === "primary"`
6. last-resort first row, with the existing development warning

Do not create a second list cache.

Do not issue a raw duplicate request to find Primary.

On Home, `/api/watchlist/list` should be zero requests unless a visible Home component genuinely requires the list itself.

A compact Watchlist Snapshot embedded in `/api/home/dashboard` is not proof that Home needs `/api/watchlist/list`.

# Contract 4 — convert `GlobalPrefetch` into true ownership, not a second page loader

`GlobalPrefetch` should not duplicate every page’s `useQuery()` calls.

A page-mounted `useQuery()` with the correct shared key already:

* loads its visible data
* stores it in React Query
* warms the cache for later navigation
* deduplicates with another consumer using the same key

Therefore:

## Keep globally only

Requests consumed by the authenticated application shell itself on almost every route.

Examples might include:

* shell-level notifications
* global alert counts
* account/session metadata

Keep only when proven by direct consumers outside individual pages.

## Home-owned

Queries required by visible Home components should be owned by Home or its mounted child components.

Do not duplicate them in `GlobalPrefetch`.

When Home and another page share a key, Home’s query naturally warms that destination page.

## Destination-page-owned

Full page datasets should normally be owned by the destination page.

Do not add a duplicate global prefetch merely to avoid a future navigation request.

## Optional idle warmups

A genuinely useful likely-next-route warmup may remain only when all of these are true:

1. It is compact.
2. It is not already requested by the current page.
3. It begins after first meaningful content.
4. It does not compete with visible current-route data.
5. It is canceled on route/auth change.
6. It has bounded retries.
7. Its value is documented.

Do not idle-prefetch the 6.3 MB Watchlist detail.
