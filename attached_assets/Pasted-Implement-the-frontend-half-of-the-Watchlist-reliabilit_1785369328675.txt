3. HANDLE CACHE WARMING WITHOUT FALSE EMPTY STATES
──────────────────────────────────────────────────────────────────────────────

Treat these backend statuses as actively warming:

- miss_syncing
- partial_syncing
- stale_syncing

They are not legitimate empty results.

Required behavior:

A. Warm cache hit

Render Upcoming and Recent immediately.

B. Stale data while refreshing

Render the stale cards immediately.

Show a subtle existing-style refreshing indicator if appropriate.

Do not blank the cards while refreshing.

C. Cold cache with no Last Known Good data

Show:

Loading earnings…

or reuse an existing loading skeleton.

Do not show:

No upcoming earnings for this watchlist.

D. Partial synchronization

Render matching cached cards that already exist.

Continue refreshing until the response settles.

E. Query error or proxy timeout

- preserve prior successful data for the exact same query key
- show a retryable error indicator
- do not replace cards with an empty array
- do not claim there are no earnings

Only show:

No upcoming earnings for this watchlist.

when all are true:

- canonical membership loaded successfully
- membership is non-empty
- request succeeded
- cache_status is settled, not syncing
- stale is false
- Upcoming is genuinely empty

Only show the Recent equivalent after the same settled-success conditions.

Polling behavior:

- refetch every 4 seconds only while cache_status is one of the syncing states
- stop immediately when the response becomes hit/refreshed/settled
- bound automatic warming polling to approximately 90 seconds
- after the bound, leave a manual retry control rather than creating a permanent loop
- switching Upcoming/Recent must not affect polling
- do not poll on settled empty results
- do not poll on an unresolved/disabled query

Use the React Query version and patterns already installed in the repository.

Do not use a global “previous response” that could display Primary data under
Favorites. Last Known Good behavior must remain scoped to the exact query key.
